۰۱.

مقدمه: بحران همگام‌سازی و معماری سنتی Request-Response

در روزهای ابتدایی توسعه میکروسرویس‌ها، عمده مهندسان برای ارتباط میان سرویس‌ها به پروتکل‌های مبتنی بر HTTP/REST یا gRPC همگام (Synchronous) روی می‌آوردند. این رویکرد در اسکیل‌های کوچک کاراست، اما با افزایش بار شبکه و زنجیره‌وار شدن درخواست‌ها، با اثر مخرب Cascading Failures مواجه می‌شویم؛ جایی که کندی یا توقف سرویس احراز هویت یا درگاه پرداخت، کل زنجیره را به بن‌بست می‌کشاند.

حرکت به سمت معماری رویدادمحور (EDA - Event-Driven Architecture) سرویس‌ها را از وابستگی زمانی و موقعیتی آزاد می‌سازد. در این مدل، یک سرویس وقوع یک رخداد تجاری مانند OrderPlaced را در شبکه برادکست می‌کند بدون آنکه نگران باشد کدام مصرف‌کنندگان و در چه زمانی آن را دریافت و مصرف خواهند نمود.

۱. الگوی Transactional Outbox

مسئله ۲-Phase Commit در سیستم‌های توزیع‌شده فاجعه‌بار است. چطور می‌توان یک رکورد در دیتابیس را ذخیره کرد و همزمان یک پیام به کافکا فرستاد بدون اینکه ریسک ناهماهنگی وجود داشته باشد؟ راهکار، استفاده از Outbox Table در همان تراکنش ACID دیتابیس محلی سرویس و سپس نشر آن توسط ابزارهایی چون Debezium (CDC) به بروکر است.

۲. مصرف‌کننده با تضمین تکرارپذیری (Idempotent Consumer)

در دنیای شبکه‌های توزیع‌شده، گارانتی «حداقل یک‌بار ارسال» (At-least-once delivery) امری استاندارد است. این یعنی پیام‌های تکراری حتماً رخ خواهند داد. کانسومر شما باید با بهره‌گیری از یک Event-ID یکتا و ذخیره آن در کش موقت Redis یا جدول پایگاه‌داده، پیام‌های پردازش‌شده را بدون اعمال مجدد تغییر رد (Acknowledge) کند.

warning

۳. مکانیزم Dead Letter Queue (DLQ)

پیام‌هایی که به دلیل دیتای خراب (Poison Pills) مکرراً با خطا مواجه می‌شوند نباید صف را متوقف کنند (Block). با تنظیم استراتژی Retry Exponential Backoff، در صورت شکست سوم، پیام به همراه استک خطای ثبت‌شده به صف مجزای DLQ فرستاده می‌شود تا تیم مهندسی بدون قطعی سیستم آن را بازبینی کند.

۰۴.

پیاده‌سازی عملی: کانسومر مقاوم در TypeScript

کد زیر نمونه استاندارد کانسومر ایمن با KafkaJS است که الگوی Idempotent و Acknowledgment را بر اساس پردازش پیام پیاده‌سازی می‌نماید:

order-consumer.ts producer.ts schema.proto 
import { Kafka, EachMessagePayload } from 'kafkajs';
import { redisClient } from './redis.service';

export async function processOrderConsumer() {
  // 1. Initialize client with backoff retry strategy
  const kafka = new Kafka({
    clientId: 'payment-service-consumer',
    brokers: ['kafka-broker-1:9092', 'kafka-broker-2:9092'],
    retry: { retries: 5, initialRetryTime: 300 }
  });

  const consumer = kafka.consumer({ groupId: 'orders-processing-group' });
  await consumer.connect();
  await consumer.subscribe({ topic: 'orders.events.v1', fromBeginning: false });

  await consumer.run({
    eachMessage: async ({ topic, partition, message }: EachMessagePayload) => {
      const eventId = message.headers?.['x-event-id']?.toString();
      
      // 2. Check Idempotency Token via Distributed Cache
      const isProcessed = await redisClient.get(`evt:processed:${eventId}`);
      if (isProcessed) {
        console.warn(`Duplicate Event ${eventId} skipped successfully.`);
        return;
      }

      try {
        const payload = JSON.parse(message.value?.toString() || '{}');
        await executePaymentTransaction(payload);

        // 3. Commit idempotent TTL flag (24h Window)
        await redisClient.set(`evt:processed:${eventId}`, '1', 'EX', 86400);
      } catch (err) {
        await routeToDeadLetterQueue(topic, message, err);
      }
    },
  });
}
